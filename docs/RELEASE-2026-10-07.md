## Independently releasable Next 15 changes

- Save blog content **before** social delivery. One DynamoDB transaction writes
  the post and both provider intents. Provider failures cannot lose the post.
- Require `If-Match: "revision"` for edits and deletion. Legacy posts without a
  revision use `"0"` once. Missing preconditions return 428; stale writes return
  409 and leave editor text visible. The server increments revisions atomically.
- Require a UUID v4 `Idempotency-Key` for creates. A permanent receipt returns the
  same saved post after a lost response; reuse for different content is rejected.
  Existing slugs remain unchanged. New collisions are resolved conditionally.
- Recheck the configured owner on admin/API access. Use distributed fixed-minute
  limits: 30 post mutations and 10 delivery invocations per minute, shared across
  instances, with 429/Retry-After. Persistence failure fails closed. These limits
  cover authenticated writes, not public read traffic or Google's sign-in flow.
- Keep per-provider durable outbox state, immutable active attempts, provider
  references, capped exponential backoff (30s to 15m, eight attempts), and status
  in the admin screen. Each invocation scans at most 100 records and processes
  one operation. A persisted scan cursor avoids starving later records. The
  editor requests up to two successive invocations after a save/delete.
- Bluesky creation uses a stable `putRecord` key and timestamp. Edits/deletes use
  retained references; account DID must match. Mastodon creates use a stable
  `Idempotency-Key`; edits/deletes reuse IDs. Already-absent Mastodon deletes
  succeed. Provider errors are not logged with content/tokens.
- Failed deletions retain their targets. Deleting a blog post immediately hides
  it and clears its title/body/link/social text, retaining a small tombstone and
  delivery metadata until reconciliation. Nothing is automatically purged.
- Newer edits cannot be overwritten by a delivery acknowledgement. Unstarted
  changes coalesce; started operations finish before newer desired content is
  processed. An unpublish is immediate on the blog; social removal can lag.
- Keep account fingerprints with remote references. Changing a Mastodon token
  conservatively requires review even if it belongs to the same account.
- Paginate post scans and exclude control records/tombstones everywhere. Public
  post responses omit private delivery text and keep no-store behavior.

## Deliberate limits on retry and recovery

External provider calls and DynamoDB do not share a transaction. This is not an
exactly-once delivery claim. Mastodon documents idempotency retention of **up to
one hour**; automatic create retries stop at 50 minutes from the first attempt.
An instance may retain a key for less time, so its actual behavior still needs
acceptance testing. A worker has a 120-second exclusive claim and a 15-second
provider abort budget (a separately bounded preview fetch can finish later).
Expired claims are **not stolen**: they become `interrupted_delivery` and their
completion token is invalidated. This trades automatic crash recovery for avoiding
unknown duplicate sends or stale updates.

`blocked` entries remain visible after further edits and require operator review.
There is deliberately no button that resets an ambiguous create and sends again.
For `interrupted_delivery`, `ambiguous_create_requires_reconciliation`,
`retry_limit_requires_review`, or `account_configuration_changed`:

1. Preserve the exact outbox item and stop the affected worker; confirm no old
   invocation can still reach a provider. Do not delete the item or receipt.
2. Verify the configured account and actual provider result using read-only
   provider access. For Bluesky inspect the stable record key (or retained URI).
   For Mastodon locate the exact status/ID; absence must be established, not
   inferred from a timeout or expired idempotency key.
3. Propose one conditional repair for Jim's approval: record a verified remote
   reference/completed revision, retry the same operation if proven safe, or
   rebind the account after checking ownership. Preserve a newer desired revision.
   Update post reference metadata and outbox state atomically; require the saved
   active operation ID/revision in the repair condition.
4. Only after approval apply that scoped repair and dispatch. Never blindly
   clear an active operation, replace its create key, or replay an old snapshot.

No actual-provider repair, deletion, or historical recovery was attempted here.

## Runtime configuration and rollout bundle

The existing table is reused; no new table, index, TTL setting, bulk backfill, or
unpublished-draft migration is required. New keys use `!outbox#`, `!create#`,
`!rate#`, and `!delivery-cursor`. Legacy provider IDs seed the queue on first edit.

The deployment role needs existing table `GetItem`, `Scan`, `PutItem`, and
`UpdateItem` permissions, including control-key access and transactional use.
AWS applies the underlying item permissions to transactions; there is no new
standalone `TransactWriteItems` IAM action to grant. Check for explicit
`dynamodb:EnclosingOperation` or leading-key denials before publication; no live
IAM change was made. The tests use the actual DynamoDB Local transaction engine.

Secrets were removed from `next.config.env`. Amplify's existing server runtime
`.env.production` mechanism is retained with an explicit name allowlist, overwrite
instead of append, literal-value encoding, and git exclusion. The encoder is
round-trip tested with Next's environment parser. It rejects unrepresentable
values without printing them. This does **not** eliminate secrets from deployment
artifacts; runtime secret-store migration is a separate deployment decision.
Only the build SHA is eligible for compile-time substitution.
